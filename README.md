# riglane-catalog

The public catalog of shared [Riglane](https://riglane.dev) workflows.

**Your code never lives here.** An entry is a *pointer*: it names a workflow in
**your** repository at an exact commit, plus a machine-generated inventory of
everything that workflow can execute. You keep ownership, your git history and
your release cadence.

## Publishing a workflow

You do not need permission and you do not need to contact anyone.

1. Put the workflow in a **public repository** of yours and commit it. The
   directory holding `workflow.yaml` must be named exactly like the workflow
   (one identity: entry id = workflow name = directory name).
2. Generate the capability inventory:

   ```bash
   riglane catalog pack path/to/<id> --out entry.lock.yaml
   ```

3. **Fork** this repository (one button).
4. Add `catalog/<id>/` with **two files** — you can do this in the browser:

   ```
   catalog/<id>/entry.yaml        written by you
   catalog/<id>/entry.lock.yaml   generated by the CLI — never edited by hand
   ```

5. Open a pull request.

### entry.yaml

```yaml
id: nightly-repo-audit            # = workflow name = directory name
summary: One line, max 140 chars. # shown in every listing
description: >
  Longer prose. What it does, when to use it.
author: your-name
license: MIT                      # required — the license of YOUR workflow
categories: [audit]
tags: [nightly, report]
source:
  repo: https://github.com/you/riglane-workflows.git
  path: nightly-repo-audit        # directory inside the repo ('' = root)
  sha: 4f2c1a9e8b7d6c5f4e3d2c1b0a9f8e7d6c5b4a39   # FULL 40-char commit SHA
requires:
  riglane: ">=0.1"
  runtimes: ["node >=18"]
tested_on:
  - { host: Claude Code, version: "2.1.4", date: 2026-08-04, result: pass }
```

## What CI checks — and what it does not

On every pull request, automation:

- validates the shape of both files;
- fetches your workflow **at the pinned SHA** (a missing commit or a private
  repository fails the check);
- **regenerates `entry.lock.yaml` from your pinned commit and rejects the
  entry if it differs from what you submitted** — you can describe your
  workflow badly, but you cannot misstate what it runs;
- runs the engine's own workflow validator;
- rejects dangerous command shapes (pipe-to-shell, `eval`, writes into
  `~/.ssh` / shell profiles) outright;
- derives the trust level.

**CI reads. It never executes** your workflow, your scripts, or anything else
you submitted. A human then looks at exactly one thing: whether the entry is
meaningful and not spam — *not* whether it is safe. Nobody can establish that
by reading, and claiming otherwise would be worse than saying nothing.

## Levels

- **Verified** — the workflow declares **no shell surface at all**: no script
  tools, no decider scripts, no bundled scripts or MCP servers. Established by
  a linter, not by a reviewer's judgement — you can tell before submitting.
- **Community** — everything else. Listed, described, **never approved**.

## Updating your entry

Commit in your repository, then open a small pull request here updating
`source.sha` and the regenerated lock. Users are never moved silently — their
installs stay pinned until they run `riglane update <id>` and accept the diff.

## Revocation

`revoked.json` at the repository root is the emergency brake: the CLI refuses
to install anything listed there. Revocations are proposed by pull request;
maintainers merge them with priority. If you believe an entry is malicious,
open an issue immediately.

## Local validation

Run exactly what CI runs:

```bash
npm ci
node scripts/validate-entries.mjs            # all entries
node scripts/validate-entries.mjs <id> …     # specific entries
```

`npm ci` is required, not optional: the validator spawns the engine CLI as
`node <resolved entry file>` with a real argument array, and it deliberately
does **not** fall back to a `riglane` on your PATH. On Windows that is a `.cmd`
shim which can only be spawned through a shell, and a shell would put a
submitter's `source.path` on a command line. When nothing is resolvable the
validator refuses with an actionable message rather than taking that route.

Working from a riglane source checkout instead of an install:

```sh
RIGLANE_CLI=/path/to/riglane/dist/cli/index.js node scripts/validate-entries.mjs
```
